# PRD Handoff

使用繁體中文。使用者先與高級模型討論 PRD，再由 cheap model 接手實作。文件必須讓沒有先前聊天內容的接手者知道要做什麼、如何判斷完成、哪些未決事項不能自行猜測。此 skill 不會切換模型或自動建立新 task。

## 查證與需求討論

1. 讀取適用的 `AGENTS.md`、`docs/DEVELOPMENT_SPEC.md` 及相關已接受決策，檢查本次功能的實作與測試。上述路徑以專案根目錄為基準。
2. 區分「程式已實作」「需求已確認但未實作」「提案／待確認」。文件與實作不一致時列出差異及來源，不把舊進度當現況，也不以現行實作取代已確認的產品目標。
3. 沿用對話中已確認的決定。影響範圍、資料契約或驗收的未決事項，提出具體建議並向使用者釐清；繼續整理不受影響內容，不重問已回答的問題。

## PRD 必備內容

依變更大小縮短篇幅，保留適用資訊；不適用的部分明示原因。沿用使用者指定或專案既有文件位置，新文件可置於 `docs/prd/<feature>.md`。交付時提供實際路徑。

### 目標、範圍與狀態

- 說明使用者的問題與完成後可觀察的改善、本次包含及不包含的功能、開始實作的依賴。
- 標示草案、待確認或可交接。可交接範圍不得留下會迫使接手者自行決定的阻塞問題；部分可交接時，明列能先做的任務。

### 使用流程與狀態

- 以具體情境描述「起始狀態 → 操作／事件 → 系統結果」。
- 涉及 UI 時，定義按鈕何時可用、成功後更新哪些資料，以及相關 loading、empty、error、retry 行為。
- 涉及寫入時，描述失敗、重複操作及狀態過期的結果；不要只寫「處理錯誤」或「避免重複」。
- 將本次相關產品限制寫成可檢查規則，避免「智慧推薦」「體驗良好」等不可驗收的要求。

### 資料與介面

- 引用已確認契約的文件章節、型別或 schema，標示本次增量與確認狀態。
- 必要欄位交代型別、必填／可省略、nullable、預設值、enum、單位／時區及範例；未決定的值不得寫成事實。
- API 變更需要詳細契約時，使用可用的 `api-contract` skill，或在本文件補齊相同資訊；不要維護互相矛盾的兩份 schema。

### 實作交接

將產品要求與實作指示分開，每個可獨立驗證的任務包含：

| 欄位 | 內容 |
|---|---|
| 任務 ID／owner | 明確工作目標與負責角色 |
| 依賴 | 前置任務、已確認契約、fixtures 或環境 |
| 修改範圍 | 已查證的檔案／模組；新路徑標為預計新增 |
| 實作要求 | 要產生的行為、沿用的功能及不可違反的限制 |
| 驗證 | 輸入、預期結果與適用檢查指令 |

Frontend、Backend A、Backend B 的任務遵循專案分工。標明可同時進行的工作與整合順序，但不因此自行派送工作或建立 task。不要猜測函式、套件或未存在的檔案。

### 驗收與未決事項

- 用具體 Given／When／Then 或同等清楚的案例涵蓋成功流程及本次相關失敗邊界。
- 每個需求對應任務及可觀察驗收結果；跨前後端功能包含整合情境。
- 檢查指令寫明執行目錄及必要環境；區分「接手者需執行」與「本次已執行」。
- 未決事項逐項列出問題、建議、決策者及被阻塞任務。已有授權或答案時直接使用，不增加確認流程。

## 交付前檢查

用「只拿到此文件與 repository」的視角檢查：能否找到依據、確認任務順序、實作狀態轉換並判斷完成？移除「同前」「依討論」「適當處理」等依賴隱藏脈絡的描述。

確認沒有把提案寫成既有 API、沒有擴大 MVP、沒有漏掉本次涉及的 owner。變更已確認產品流程或核心名詞時，同步 `docs/product-flow.md` 或 `docs/domain-model.md`；重要已確認決策依專案慣例記錄於 `docs/decisions/`。草案不直接改寫成共用規格中的既定決策。

交付文件、可實作範圍及待決定事項。只要求 PRD 時完成交接文件即可，不擅自進入產品實作。
